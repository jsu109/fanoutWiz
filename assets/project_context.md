# fanoutWiz Project Context

## Purpose

fanoutWiz is a configurable generic BGA fanout structure generator.

The application is not an autorouter.

The goal is to generate deterministic, reusable BGA breakout structures that provide a high-quality starting point for PCB routing.

The generated geometry should:
- completely fanout all BGA pads
- obey configurable manufacturing constraints
- support different breakout strategies
- produce editable PCB geometry
- remain independent from final signal routing decisions

Future objectives may include more intelligent routing assistance, but the current focus is structured fanout generation.

---

# High-Level Architecture

The application follows this flow:

BGA Definition         |         v Structure Configuration         |         v Structure Generator         |         v Fanout Geometry         |         v Fanout Compiler         |         v Render / Export

---

# Current Core Concepts

## Structure Configuration

The active fanout configuration is stored as structureConfig.

This contains:

structureConfig     |     +-- preset     |     +-- bga     |     +-- rules     |     +-- policy     |     +-- spacing     |     +-- clineSeg     |     +-- via

The controller manages updating and switching between structure presets.

Changing a structure preset creates a new configuration while preserving compatible user overrides.

---

# Structure Generation

The controller builds the current structure through:

controller::buildStructure()

which calls:

model::structure::createStructure

The generated structure contains:

structure     |     +-- bga     |     +-- pads     |     +-- fanout     |     +-- vias

The structure is the geometric representation of the selected fanout strategy.

---

# Fanout Representation

Current pipeline:

structure     |     v fanout     |     v model::fanoutCompiler::compile     |     v compiled segments

The compiler converts the fanout representation into drawable routing geometry.

Current output includes:

- cline segments
- vias
- pads

---

# Future Data Model Direction

The application should evolve toward an intermediate fanout representation:

FanoutStructure         |         +-- EscapePath[]                 |                 +-- Segment[]                 |                 +-- Via[]

An EscapePath represents the complete breakout geometry for a single BGA pad.

Example:

Pad  |  +-- cline segment  |  +-- cline segment  |  +-- via  |  +-- endpoint

The endpoint is generated by the fanout algorithm.

It is not a routing destination.

It is calculated from:

- BGA dimensions
- pitch
- pad size
- fanout strategy
- trace width
- spacing
- via dimensions
- routing layer availability

---

# Fanout Strategies

Current and planned strategies:

## Basic Escape

Simple breakout:

pad  |  |  via

## Dogbone / Quadrant Escape

Offset breakout:

pad  |  |  +---- via

## Via-in-pad

Direct transition:

pad  | via

Each strategy should generate the same intermediate representation:

EscapePath[]

The renderer should not need to know which strategy generated the geometry.

# Controller Responsibilities

controller/bgaController.tcl currently manages:

## Configuration

controller::updateStructureConfig controller::setStructurePreset

Responsibilities:
- update configuration values
- switch fanout structures
- preserve compatible overrides

---

## Structure Building

controller::buildStructure

Creates the current generated fanout structure.

---

## Frame Collection

controller::collectFrame

Converts the generated structure into render-ready data.

Current process:

structure     |     v fanout compiler     |     v segments     |     v normalised render features

The render frame contains:

frame  |  +-- bga  +-- pads  +-- segs  +-- vias  +-- featureIndex  +-- world dimensions

---

# Rendering Architecture

Rendering consumes compiled geometry.

The renderer should remain separated from generation.

Current flow:

Fanout Geometry         |         v model::fanoutCompiler         |         v render::fanout::draw

The renderer should only:
- draw pads
- draw clines
- draw vias
- display generated geometry

It should not make routing decisions.

---

# Design Principles

## Keep Tcl Dictionary Based Models

The application currently uses Tcl dictionaries for:
- configurations
- structures
- generated geometry

Continue using this approach.

---

## Separate Planning From Rendering

Generation decides:

- geometry
- layer assignment
- via placement
- escape length
- endpoint positions

Rendering only displays results.

---

## Avoid Hard-Coded Geometry

All geometry should derive from:

- BGA definition
- routing rules
- selected strategy

---

## Maintain Registry-Based Architecture

Existing systems such as:

fanout::structures::registry fanout::structures::viaTypes

should remain the mechanism for registering reusable strategies.

---

# Current Development Objective

Refactor the fanout generation model so that:

Input:

BGA Definition Routing Rules Fanout Strategy

Produces:

FanoutStructure      EscapePath[]          Segment[]          Via[]

This creates a reusable parametric BGA fanout engine while keeping the architecture open for future routing assistance.
